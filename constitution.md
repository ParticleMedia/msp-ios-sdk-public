# MSP iOS SDK Development Constitution

> **Version**: 1.1  
> **Last Updated**: 2026-01-09  
> **Status**: Active

This document defines the immutable core development principles for the MSP iOS SDK project. All contributors, including human developers and AI Agents, must adhere to these principles unconditionally when planning technical designs and implementing code.

---

## Article I: The Principle of Automation & Determinism

**Core Tenet**: Trust scripts, not manual actions. Every build must be reproducible.

**1.1 (Automation First)**: Any manual operation repeated more than twice must be scripted. This project provides a powerful suite of automation tools (`msp-release.sh`, `xcframeworks/`, `spm-sync/`); they must be used.

**1.2 (Deterministic Builds)**: [Non-Negotiable] Directly modifying `.xcodeproj` or `.xcworkspace` files is strictly forbidden. All changes to the project structure must be accomplished by modifying the appropriate `*.yml.template` files and then running XcodeGen. This is the bedrock of build determinism.

**1.3 (Single Source of Truth - SSOT)**: The root `Podfile` is the single, authoritative source for all third-party dependency versions. Any version change must begin by modifying this file.

**1.4 (Sanctity of the Release Process)**: [Highest Priority] When resolving any issue related to "release," "build," "dependency," or "environment," temporary manual workarounds are strictly forbidden.

> **Example Scenario**: A release process fails due to a missing XCFramework.
>
> ❌ **Incorrect (Unconstitutional) Action**: Manually running a one-off script to generate the missing artifact.
>
> ✅ **Correct (Constitutional) Action**:
> 1. **Analyze**: Identify why the main build script (e.g., `./Scripts/xcframeworks/build-core.sh`) failed to generate the artifact.
> 2. **Fix**: Modify the build script itself or its configuration to resolve the issue at its root.
> 3. **Verify**: Re-run the complete, high-level automation script (e.g., `msp-release.sh --tier Preflight`) to validate the fix.

---

## Article II: The Validation-Driven Imperative

**Core Tenet**: The value of all changes is proven by automated validation.

**2.1 (The Validation Loop)**: Any meaningful change (e.g., a new feature, a bug fix) must successfully pass all relevant automated validation gates.

**2.2 (Local Verification First)**: Before committing code, it is mandatory to run at least `./Scripts/target-switching/round-trip-test.sh` to ensure compatibility across all three SDK modes.

**2.3 (Pre-Release Validation)**: For changes intended to be merged into the main branch, it is strongly recommended to run `./Scripts/msp-release.sh --tier Preflight <version>` to perform a more comprehensive build and integration check.

---

## Article III: The Principle of Modularity & Protocol-Orientation

**Core Tenet**: Every module and every class should do one thing well. Interactions should be defined by protocols, not concrete implementations.

**3.1 (Module Cohesion)**: Core modules are responsible for generic logic; Adapters are responsible for interfacing with third-party SDKs. It is strictly forbidden to import any third-party ad SDK headers directly within a Core module.

**3.2 (Protocol-Oriented Design)**: Adhere to established design patterns like the `AdNetworkAdapter` protocol. Define small, targeted protocols instead of creating monolithic "God Classes" or "God Protocols."

**3.3 (UI/Logic Separation)**: UIKit code (e.g., `UIViewController`) is responsible only for presentation and user response. It must never contain business logic (e.g., ad bidding algorithms, complex data transformations).

---

## Article IV: The Principle of Core Swift Practices

**Core Tenet**: Write idiomatic, robust, and maintainable Swift code.

**4.1 (Value-Types First)**: Must prefer `struct` and `enum` for modeling data. Use `class` only when reference semantics or Objective-C interoperability are explicitly required.

**4.2 (Immutability by Default)**: Must prefer `let` for declaring constants. Use `var` only when a value must be mutated within its lifecycle.

**4.3 (Safe Error Handling)**: [Non-Negotiable] Errors must never be "swallowed" (`Result` types must be handled). Force-unwrapping optionals (`!`) is forbidden unless its safety is 100% guaranteed (e.g., `IBOutlet`). All `public` and `open` APIs must have clear Swift DocC comments.

---

## Governance

This Constitution holds the highest authority, superseding any instructions in `CLAUDE.md`, `Agents.md`, or any single interactive session. Any plan generated by an AI Agent must first undergo a "Constitutional Review" to ensure every step complies with these principles.
